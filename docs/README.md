# ドキュメントの構成と規則

このリポジトリのドキュメントの置き場所と、書くときの規則を定める。ドキュメントを足す・直す・移すときは、先にこの文書を読む。

## 構成

ドキュメントは、今の挙動を書く仕様書 (`spec/`)、仕組みの全体像 (`architecture.md`)、運用の方針 (`operations.md`)、更新しない記録 (`archive/`) に分ける。

| ファイル | 書くこと |
|---|---|
| [`spec/ui.md`](./spec/ui.md) | 画面の構成・URL・共通部品・見た目 |
| [`spec/run-overview.md`](./spec/run-overview.md) | ラン全体・階の画面に出す値と集計方法 |
| [`spec/combat-stats.md`](./spec/combat-stats.md) | 戦闘の画面に出す値と集計方法 |
| [`spec/user-pages.md`](./spec/user-pages.md) | ログイン、ユーザーページ、ランの公開・非公開・削除 |
| [`spec/data-sources.md`](./spec/data-sources.md) | mod がゲームのどこから何を取るか、誰の行為として送るか、その根拠にしたゲームの挙動 |
| [`spec/api.md`](./spec/api.md) | mod ⇄ backend ⇄ web の HTTP API と event の形 |
| [`architecture.md`](./architecture.md) | 3 層の構成、データの流れ、デプロイ、カタログの作り方 |
| [`operations.md`](./operations.md) | サーバの運用と配布の方針、ゲーム更新時の手順 |
| [`archive/`](./archive/) | 過去の計画・設計判断・調査記録。更新しない |

## 仕様書に書くこと

`spec/` の仕様書には、今の実装が満たすべき挙動だけを書く。経緯、確定した日付、以前の版との違いは書かない。
経緯はコミットメッセージに書き、API の破壊的変更だけは `spec/api.md` の「バージョン履歴」の表に 1 行足す。

1 つの事実は 1 つのファイルにだけ書く。ほかのファイルでその事実が要るときは、写さずにリンクする。
例えば、mod がどの Hook から何を取るかは `spec/data-sources.md` にだけ書き、`architecture.md` からはリンクする。
写した表は、元の表を直したときに直し忘れて食い違う。

まだ実装していないことは、仕様書の「既知の制約」の節に、何が無いかを 1 行で書く。将来の計画の文書は作らない。

## 仕様書を足す・置き換えるとき

新しい仕様書や節で既存の節を置き換えたら、置き換えた側を同じコミットで消す。
「この節は古い」という断り書きを残して、古い節を置いたままにしない。

仕様書を足したら、この文書の「構成」の表と、リポジトリ直下の `CLAUDE.md` の仕様書の一覧に 1 行足す。

## 参照の書き方

ほかの文書の節は、節の番号ではなく見出しの名前で参照する (例: `combat-stats.md「貢献スコア」`)。
節の番号で参照すると、節を足したり消したりしたときに、番号のずれた参照が別の節を指してしまう。
そのため、仕様書の見出しには番号を付けない。見出しの名前を変えたら、`grep` でその名前を参照している箇所を探して直す。
コードのコメントから仕様書を参照するときも同じ書き方にする。

## 更新しない記録

`archive/` の文書は、書かれた時点の計画・判断・調査の記録として残す。中身を直さず、新しい情報も書き足さない。
今も正しい事実が archive の文書にしか無いと分かったら、その事実を仕様書に移す。
仕様書とコードのコメントからは、archive の文書を参照しない。

## ゲームの挙動を書くとき

デコンパイルで確かめたゲームの挙動は、`spec/data-sources.md` の「ゲームの挙動」に書く。
ゲームの版が上がって挙動が変わったら、古い挙動の記述を消して、新しい挙動を書く。
